# Octane Research Studio — передача работы другому ИИ

Состояние на **13 октября 2026 года**. Этот файл передаёт контекст проекта и незавершённые задачи. Перед изменениями прочитайте также корневой `README.md`, проверьте `git status` и текущий код: состояние после этой даты может измениться.

## 1. Что нужно пользователю

Репозиторий: https://github.com/makkeeva/octane-research-studio

Приватное приложение для следующего процесса:

1. Взять статью из https://octane.rent/blog/.
2. Подготовить формальный аналитический отчёт, сохранив проверяемые факты и добавив независимые первичные источники.
3. Создать PDF с активной ссылкой на исходную статью Octane, библиографией, реестром фактов и раскрытием помощи ИИ.
4. После проверки человеком подготовить и опубликовать материал в Internet Archive, OSF, Figshare и Zenodo.

Пользователь выбрала **локальный запуск через Docker на своём ноутбуке**. Docker уже установлен. Порт **3000 занят**, поэтому внешний адрес приложения — **http://localhost:3001**. Внутри контейнера сервер использует порт 3000.

Нужны сохранение отчётов и подключений, понятные ошибки и работа после перезапуска. Пользователь предпочитает бесплатную модель/API и сообщила, что на ноутбуке установлена Ollama. Предлагайте конкретные действия и завершайте разрешённую работу без повторных общих подтверждений. Объясняйте команды по-русски и всегда уточняйте в инструкции, где их выполнять: на ноутбуке, в Codespaces или в среде агента.

## 3. Ближайшая задача: запустить Docker на ноутбуке и сохранить данные

Пользователю уже выдан файл **`octane-local-backup.enc.json`**. Он должен находиться в папке `Downloads`/«Загрузки» на ноутбуке либо в корне скачанного проекта. Его содержимое зашифровано; файл не хранится в GitHub. Ссылки на скачивание из предыдущего чата могут стать недоступны — при необходимости копию можно получить заново из исходного Codespace.

На ноутбуке нужно открыть Docker, дождаться запуска и выполнить в терминале:

```bash
git clone https://github.com/makkeeva/octane-research-studio.git
cd octane-research-studio
```

Если проект уже скачан, зайти в существующую папку и выполнить `git pull --ff-only`, предварительно сохранив собственные изменения.

**macOS / Linux:**

```bash
bash scripts/docker-local.sh
```

**Windows PowerShell:**

```powershell
powershell -NoProfile -File scripts/docker-local.ps1
```

Docker Desktop на Windows должен использовать Linux containers. Не отключайте системные защиты автоматически при ошибке PowerShell: сначала выясните конкретную причину.

При найденной копии скрипт спросит **прежний пароль приложения Octane**. Это пароль входа в студию, не пароль GitHub и не токен площадки. Ввод в терминале скрыт. После восстановления не нужно заново вводить токены.

Если файл в другом месте:

```bash
bash scripts/docker-local.sh "/полный/путь/octane-local-backup.enc.json"
```

```powershell
powershell -NoProfile -File scripts/docker-local.ps1 -BackupFile "C:\полный\путь\octane-local-backup.enc.json"
```

После успешного запуска открыть **http://localhost:3001** и войти прежним паролем приложения. Убедиться, что доступны оба отчёта, PDF и сохранённые подключения. Если скрипт предлагает придумать новый пароль вместо восстановления, сначала проверить путь и имя копии; пользователю нужен перенос существующего рабочего пространства.

Скрипты выполняют восстановление через официальный образ Node 24; Node.js на ноутбуке устанавливать не нужно. Они задают `PUBLIC_URL=http://localhost:3001`, сохраняют исходный пароль, используют том `octane-research-studio_studio-data` и ждут healthcheck. Существующую базу не перезаписывают. При наличии базы и отсутствии прежнего пароля запуск останавливается, чтобы не потерять доступ к сохранённым ключам.

Команды управления, выполняемые в папке проекта на ноутбуке:

```bash
docker compose ps
docker compose logs --tail=100 studio
docker compose stop
docker compose up -d
```

`docker compose down` сохраняет том. **`docker compose down -v` и удаление тома уничтожают данные** — не использовать для обычного исправления ошибки. Политика `restart: unless-stopped` помогает после перезапуска Docker; доступ прекращается, когда ноутбук спит или Docker выключен.

**Самодиагностика «почему не идёт генерация».** Безопасный read-only скрипт `scripts/doctor.mjs` проверяет три главные причины (нет ключа Gemini / исчерпана квота или модель недоступна / данные не восстановлены и база пустая), не выводя секретов и ничего не меняя. Запуск внутри контейнера:

```bash
docker compose exec studio node scripts/doctor.mjs
docker compose exec studio node scripts/doctor.mjs --check-gemini   # read-only проверка доступа к модели, без расхода квоты
```

Он читает базу в режиме readOnly, печатает количества документов/подключений/публикаций, пытается расшифровать сохранённые ключи текущим APP_PASSWORD (так выявляется смена пароля) и показывает текст последней неудачной работы генерации — именно он даёт точную причину.

Сессии действуют 12 часов; в базе сохраняются HMAC-хэши сессионных токенов. Сервер проверяет Host и Origin. Не удалять эти проверки, чтобы исправить ошибку адреса: задавать правильный PUBLIC_URL.

В Docker Compose явно установлены `PORT=3000`, `HOST=0.0.0.0`, `DATA_DIR=/app/data`; снаружи опубликован `127.0.0.1:${STUDIO_PORT:-3001}:3000`.

## 6. Генерация: что уже исправлено и что ещё проверить

По умолчанию используется Gemini `gemini-2.5-flash-lite` с сохранённым ключом. Работа разделена на два запроса:

1. Поиск первичных источников через Google Search и подготовка заметок.
2. Структурированный JSON-отчёт по найденным источникам.

При отсутствии Gemini ключа основная версия может использовать `OPENAI_API_KEY` / `OPENAI_MODEL` из окружения, по умолчанию `gpt-4.1`. Это отдельный платный API. **Не добавлять такой ключ и не включать биллинг без указания пользователя.** Ошибка или исчерпание квоты Gemini не запускает платный fallback.

Исправлены прежние ошибки структуры: громоздкая JSON-схема, неверный статус `verified`, повторение длинных URL в ответе, превышение длины `claims[].evidence`. Модель выбирает короткие ID источников; URL вставляет сервер из реестра результатов поиска. Допустимые статусы факта: `supported`, `unverified`, `conflict`; человеческая проверка хранится отдельно в `reviewed`.

Разрешена одна попытка исправить только слишком длинные текстовые поля, сохраняя те же факты и источники. HTTP-ошибки, квоты, неподтверждённые ссылки и другие смысловые ошибки не повторяются автоматически. Пользователь получает безопасное сообщение с конкретным полем/лимитом; исходный ответ модели и ключи в ошибку не включаются.

Генерация запускается коротким HTTP-запросом и продолжается на сервере. Этапы и ошибки сохраняются в SQLite; UI опрашивает статус. Повторный клик во время активной генерации не создаёт вторую работу. Перезапуск сервера помечает незавершённую работу прерванной; модель не вызывается автоматически заново.

**Незавершённые задачи качества:**

- Импорт сохраняет текст, но может терять исходные URL ссылок/iframe и захватывать посторонние блоки страницы. Улучшить выделение основного текста и происхождения источников.
- Gemini иногда возвращает непрозрачные Google grounding redirect URL. Проверить возможность показывать человеку понятные конечные первичные источники с сохранением происхождения ссылок и безопасной обработкой редиректов.
- Проверка наличия ссылки в выдаче поиска не доказывает, что она подтверждает конкретное число. Проверять цитируемый фрагмент, единицы, дату, географию и контекст; сохранять человеческую проверку.
- Повторить генерацию на новой статье после локального запуска, проверить видимые этапы, итоговый текст и PDF. Реальный запрос расходует квоту: не запускать несколько диагностических генераций вслепую.
- Если пользователь выберет Ollama, добавить отдельный адаптер и настройки. Сначала определить доступную модель и проверить её способность выдавать нужную структуру. Ollama сама по себе не заменяет поиск реальных источников. Сейчас такого адаптера нет.

## 7. Площадки и правила публикации

| Площадка | Реализованный путь |
| --- | --- |
| Internet Archive | S3 Access Key + Secret Key. Подготовка локальная; финальная загрузка сразу публичная. Затем проверка очереди и Metadata API. |
| OSF | Personal Access Token. Отдельный приватный проект, загрузка PDF через WaterButler, отдельный переход проекта в public. |
| Figshare | Personal token, категория и лицензия из API. Приватная запись, multipart upload, отдельная публикация. |
| Zenodo | Personal token с `deposit:write`, `deposit:actions`. Черновик, загрузка, отдельная публикация. Связывание аккаунта с GitHub не заменяет токен для публикации произвольного PDF. |

Read-only проверка подключения не создаёт запись и не доказывает права на запись. Сохранённые поля в UI очищаются после сохранения; это не удаление ключа. Сервер возвращает метаданные подключения, а не секреты.

Ранее Zenodo показал **`Access blocked due to unusual traffic`**. Не выдавать это за неверный токен и не пытаться обходить подтверждённую блокировку сменой сетевого пути, хоста или User-Agent. Для поддержки нужны Reference ID, timestamp, браузер и версия с исходной страницы ошибки. Сохранённый ключ можно перенести без автоматической повторной проверки.

В README зафиксировано уведомление OSF о прекращении создания новых проектов через API с **16 ноября 2026 года** и переходе проектов в режим чтения с **19 февраля 2027 года**: https://help.osf.io/article/744-osf-projects-api-impact. Перед дальнейшей работой с OSF проверить актуальное официальное уведомление. Текущий адаптер зависит от создания нового проекта на каждый отчёт.

Публикация требует реального автора, выбранной лицензии, прав на материал и проверки фактов. Непроверенный PDF маркируется черновиком. Формальный стиль не превращает рекламную статью в научное исследование; нужны самостоятельный анализ и честное раскрытие происхождения текста. Для Zenodo дополнительно требуется описание исследовательского вклада человека; соответствие правилам всё равно оценивает автор.

После подготовки публикации документ замораживается; изменения делаются через копию. Внешние ID сохраняются по ходу отправки. При потерянном ответе или частичной загрузке сначала проверить внешний статус и аккаунт, чтобы не создать дубль. Не сбрасывать состояние публикации и не повторять загрузку вслепую.

До публичного теста нужен проверенный конкретный документ и указание пользователя публиковать его. Подготовка приватного черновика и финальная публичная публикация — разные действия; Internet Archive не предоставляет аналогичного приватного этапа загрузки в этом адаптере.

## 8. Отдельная hosted/Sites-версия

URL: https://octane-research-studio.sf-education-4624.chatgpt.site

Код в `hosted/`: отдельная реализация с входом через ChatGPT, D1 для данных, R2 для PDF и WebCrypto vault. Это другой runtime; изменения корневого сервера не появляются в hosted автоматически. Не менять эту версию вместо локального Docker без нового указания пользователя.

## 9. Проверки при продолжении

Для изменений основной версии:

```bash
npm ci
npm run check
npm run build
npm test
```

Тесты не выполняют настоящие публикации и не тратят API-квоту. Последний подтверждённый результат основной версии — 29/29. Для изменения только документации повторный полный прогон не требуется; для новой логики запускать соответствующие проверки.

На ноутбуке проверить:

1. Контейнер действительно собран, имеет healthy-статус и доступен на localhost:3001.
2. Вход со старым паролем, наличие двух документов/PDF и сохранённых подключений после восстановления.
3. Сохранность после перезапуска контейнера.
4. Генерацию одной новой статьи с понятными этапами и без ошибки схемы.
5. Источники, реестр фактов, ссылки и кириллицу в полученном PDF.
6. При разрешённом тесте площадки — подготовку конкретного черновика и корректную фиксацию внешнего ID; финальную публикацию проверять отдельно.

При диагностике собирать текст конкретной ошибки, состояние контейнера и безопасные логи. **Не запрашивать весь `.env`, `docker compose config`, `docker inspect` или дамп базы в чат:** они могут раскрыть секреты и личные данные. Не искать пароль в истории терминала. При отсутствии доступа к ноутбуку дать конкретную команду и честно обозначить, что её выполняет пользователь.
